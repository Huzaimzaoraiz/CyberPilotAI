1. SHARED PERSISTENT POSTGRES DATABASE (CRITICAL GAP)
--------------------------------------------------------------------------------
* Current State:
  `core/database.py` is entirely an in-memory Python dictionary (`self.assets = {}`,
  `self.vulnerabilities = {}`). Data is wiped whenever the service restarts.
* Plan / Evaluation Requirement:
  A persistent shared PostgreSQL instance managed via docker-compose, acting as the
  single source of truth.
* Required Changes:
  a. Create `db/schema.sql` defining the 6 required tables:
     - `assets` (id, target, asset_type, host, port, protocol, discovered_at, status)
     - `findings` (id, asset_id, title, description, severity, cve_id, source, raw_evidence, discovered_at, status)
       * Note: `source` ('tool' | 'ai_inference') must be strictly enforced on every insert.
     - `validated_findings` (id, finding_id, exploitable, confidence_score, cvss_score, poc_exists, validation_evidence, mitre_technique, validated_at, status)
     - `attack_paths` (id, path_nodes, path_edges, cumulative_risk, break_chain_target, mitre_chain, created_at, status)
     - `remediations` (id, finding_id, attack_path_id, root_cause, fix_suggestion, code_snippet, priority, applied, created_at, status)
     - `retests` (id, finding_id, remediation_id, still_vulnerable, evidence, retested_at, status)
  b. Update `core/database.py` (or create `db/db.py`) to connect to Postgres via `asyncpg` or `psycopg2`
     connection pooling with fallback to in-memory mode when PostgreSQL is not reachable.
  c. Ensure every record follows the strict status lifecycle: `pending` -> `processing` -> `done`.

2. DOCKER & CONTAINER SANDBOXING (CRITICAL EVALUATION ITEM)
--------------------------------------------------------------------------------
* Current State:
  No `docker-compose.yml` or `Dockerfile` exists inside the platform repo. Tools execute
  locally on the host machine.
* Plan / Evaluation Requirement:
  Complete reproducible deployment with Docker. Scanning tools (Nmap, Gobuster, etc.)
  must run inside an isolated tools sandbox container or isolated Docker network so the host
  is never exposed.
* Required Changes:
  a. Create `docker-compose.yml` containing:
     - `postgres`: PostgreSQL 15 container with persistent volume `pgdata`.
     - `app`: FastAPI backend serving the platform and UI.
     - `sandbox-tools` (optional/profile-driven): Container equipped with nmap, gobuster, nikto
       with an internal Docker network interface.
  b. Create `Dockerfile` for the application container.
  c. Create `.env.example` with standard database and API credentials.

3. MISSING STANDALONE & RECON TOOLS
--------------------------------------------------------------------------------
* Current State:
  Only partial wrappers exist (e.g., `scanners.py` has basic Nmap and CPE query;
  `api_connectors.py` has basic VT/HIBP; `vuln_scanner_mcp.py` has internal regexes).
* Plan / Evaluation Requirement:
  Standalone deterministic Python functions in `tools/recon.py` with standard signatures
  returning structured JSON dicts:
  - `search_nvd(cve_id: str) -> dict`: Queries local NVD JSON feed cache or NVD REST API.
  - `exploitdb_search(cve_id: str) -> dict`: Checks for public PoC existence in ExploitDB.
  - `virustotal_lookup(target: str) -> dict`: Queries VirusTotal for domain/URL/IP reputation.
  - `hibp_check(email: str) -> dict`: Privacy-preserving breach check (k-anonymity / simulated).
  - `dns_lookup(domain: str) -> dict`: DNS records (A, MX, TXT) + SSL certificate info.
  - `phishing_score(target: str) -> dict`: Heuristic analysis + VT detection score.
  - `whois_lookup(target: str) -> dict`: Registration date, registrar, and ASN details.
  - `mitre_attack_lookup(technique_id: str) -> dict`: ATT&CK tactic/technique details.
  - `dir_bruteforce(url: str) -> dict`: Web directory and endpoint discovery.
